AUDIT TECHNIQUE DU BACKEND SUMA
Date : 20 octobre 2026
Périmètre : analyse statique du dépôt Laravel, sans accès à la base réelle et sans modification préalable du code.

======================================================================
A. RÉSUMÉ EXÉCUTIF
======================================================================

Le dépôt contient un backend Laravel assez étendu : authentification par jetons Sanctum, comptes étudiants et encadreurs, mémoires et versions, commentaires, planification et résultats de soutenance, archivage, gestion administrative et notifications. L’architecture s’appuie sur des contrôleurs API, des Form Requests, des ressources JSON, des services et des repositories.

L’état général est toutefois partiel : plusieurs parcours existent dans le code, mais leurs autorisations, leurs contrôles d’intégrité ou leurs dépendances au schéma ne sont pas cohérents. Les constats les plus importants sont :

- CRITIQUE — attribution de rôle lors de l’inscription publique : RegisterRequest accepte un role_id fourni par le demandeur ; AuthService::register l’utilise pour créer le compte. Un visiteur peut donc demander un rôle privilégié si son identifiant existe.
- ÉLEVÉ — consultations insuffisamment limitées : la liste des mémoires, le calendrier des soutenances et plusieurs vues de ressources reposent sur des policies permissives et n’appliquent pas systématiquement de périmètre par rôle ou par dossier.
- ÉLEVÉ — recherche publique d’archives : le orWhereJsonContains non regroupé dans ThesisArchiveService peut faire apparaître des archives privées dans une recherche publique par mot-clé.
- ÉLEVÉ — archive liée à une mauvaise version : l’identifiant thesis_version_id fourni lors de l’archivage est vérifié globalement, mais pas contre le mémoire archivé ni contre le type PDF.
- Autorisations administratives inégales : certaines routes sous /api/admin ne vérifient pas le rôle administrateur, notamment la suppression d’une année académique.
- Tests métier absents : les deux tests présents sont des tests d’exemple et ne couvrent ni les routes métier ni les autorisations.

L’audit est statique et en lecture seule. Aucune migration, aucun test et aucune opération sur la base réelle n’ont été exécutés. La commande non destructive php artisan route:list --json n’a pas produit de résultat dans le délai d’attente et a été arrêtée ; le catalogue ci-dessous est reconstitué à partir des déclarations de routes et de leurs contrôleurs.

Deux fichiers étaient déjà modifiés dans l’arbre de travail au début de l’audit. Les constats décrivent leur contenu actuel ; ces modifications ne proviennent pas de cet audit :

- app/Http/Controllers/Api/Thesis/ThesisController.php : store traite l’absence de profil étudiant et refuse un deuxième mémoire, y compris après suppression logique.
- app/Services/ThesisService.php : la transition approved -> archived est désactivée dans la table des transitions. L’archivage modifie néanmoins directement le statut par un autre chemin.

======================================================================
B. ARCHITECTURE LARAVEL
======================================================================

- Versions déclarées/verrouillées : PHP ^8.2 et Laravel 12.64.0 dans composer.json et composer.lock. Le runtime PHP effectivement utilisé n’a pas été confirmé.
- Organisation : contrôleurs par domaine sous app/Http/Controllers/Api, validations sous app/Http/Requests, transformations JSON sous app/Http/Resources, modèles Eloquent, services et interfaces, repositories, policies et middleware.
- Providers : les policies et bindings de services/repositories sont enregistrés via bootstrap/providers.php, AuthServiceProvider.php et RepositoryServiceProvider.php.
- Routes : le préfixe /api est configuré dans bootstrap/app.php. Un groupe commun applique auth:sanctum et active à la plupart des routes métier.
- Routes non métier : routes/web.php déclare GET / vers la page welcome. routes/console.php déclare la commande inspire. Le point de santé /up est configuré dans bootstrap/app.php.
- Frontend : aucun code Angular n’a été trouvé dans cet espace de travail. Le JavaScript présent se limite à resources/js, avec Vite et Axios déclarés dans package.json.

C. CATALOGUE DES ROUTES API
======================================================================

Toutes les URI ci-dessous sont préfixées par /api. Sauf indication contraire, les réponses métier sont JSON, généralement avec data, parfois message et meta. Les Form Requests mentionnées assurent la validation et, pour certaines, l’autorisation.

AUTHENTIFICATION

- POST /api/auth/register
  Contrôleur : AuthController::register.
  Middleware : aucun middleware d’authentification.
  Fonction/validation : RegisterRequest valide identité, email, mot de passe et rôle existant. Crée un utilisateur et un jeton Sanctum. Tables users, roles, personal_access_tokens.
  Réponse/état : 201 avec ressource d’authentification et jeton. Implémenté, mais vulnérable à l’attribution de rôle par le demandeur.

- POST /api/auth/login
  Contrôleur : AuthController::login.
  Middleware : throttle:5,1 ; route publique.
  Fonction/validation : LoginRequest valide email et mot de passe ; vérifie l’activité du compte et crée un jeton.
  Réponse/état : JSON ; erreurs 401/403 traitées explicitement. Implémenté.

- POST /api/auth/forgot-password
  Contrôleur : AuthController::forgotPassword.
  Middleware : throttle:3,1 ; route publique.
  Fonction/validation : ForgotPasswordRequest valide l’email avec exists:users,email ; envoie une notification de réinitialisation.
  Réponse/état : JSON. Implémenté, mais la validation révèle si une adresse est enregistrée.

- POST /api/auth/reset-password
  Contrôleur : AuthController::resetPassword.
  Middleware : route publique.
  Fonction/validation : ResetPasswordRequest valide le jeton, l’email et le nouveau mot de passe confirmé. Invalide les autres jetons Sanctum.
  Réponse/état : JSON et erreurs de validation. Implémenté ; aucune limitation de débit visible sur cette route.

- GET /api/auth/verify-email/{id}/{hash}
  Contrôleur : AuthController::verifyEmail.
  Middleware : signed.
  Fonction : vérifie le lien et le hash d’email du compte.
  Réponse/état : JSON. Implémenté, mais aucun middleware verified n’impose ensuite la vérification pour utiliser l’API.

- POST /api/auth/logout
  Contrôleur : AuthController::logout.
  Middleware : auth:sanctum, active.
  Fonction : révoque le jeton courant. Réponse JSON. Implémenté.

- GET /api/auth/me
  Contrôleur : AuthController::me.
  Middleware : auth:sanctum, active.
  Fonction : retourne le compte courant et son rôle. Réponse UserResource. Implémenté.

- POST /api/auth/change-password
  Contrôleur : AuthController::changePassword.
  Middleware : auth:sanctum, active.
  Validation : ChangePasswordRequest vérifie le mot de passe courant et le nouveau mot de passe confirmé.
  Fonction : modifie le mot de passe et invalide les autres jetons. Réponse JSON. Implémenté.

- POST /api/auth/profile
  Contrôleur : AuthController::updateProfile.
  Middleware : auth:sanctum, active.
  Validation : UpdateProfileRequest ; avatar validé comme image avec maximum 2 Mo.
  Fonction : met à jour le profil et stocke l’avatar sur le disque public. Réponse UserResource. Implémenté.

- POST /api/auth/resend-verification
  Contrôleur : AuthController::resendVerification.
  Middleware : auth:sanctum, active.
  Fonction : renvoie l’email de vérification. Réponse JSON. Implémenté, sans route de consultation des notifications.

E. SCHÉMA DES DONNÉES
======================================================================

Le tableau suivant décrit le schéma attendu par les migrations, pas l’état d’une base réellement consultée.

- Identité : roles, permissions, permission_role, users.
  Un utilisateur appartient à un rôle ; association rôle-permission unique par paire ; suppression du rôle d’un utilisateur restreinte ; utilisateur avec suppression logique et email unique.

- Authentification : personal_access_tokens, password_reset_tokens.
  Jetons polymorphes Sanctum et table de jetons de réinitialisation de mot de passe.

- Organisation : departments, programs, academic_years, students, supervisors.
  Code département/programme unique ; programme lié à un département ; étudiants liés à année, programme et département ; numéro étudiant unique ; profils étudiant/encadreur liés chacun à un utilisateur unique et supprimés logiquement.

- Mémoires : theses, thesis_versions, comments, thesis_status_histories.
  Un mémoire par étudiant (student_id unique) ; versions uniques par numéro pour chaque mémoire ; commentaires liés au mémoire et éventuellement à une version ; historique des statuts avec utilisateur auteur. Mémoire supprimé logiquement.

- Soutenances : defense_rooms, jury_members, defense_schedules, defense_jury_members, defense_jury_evaluations, defense_results.
  Une soutenance par mémoire (thesis_id unique) ; rôles de jurés uniques par soutenance ; évaluation unique par couple soutenance/juré ; un résultat unique par soutenance.

- Archives : thesis_archives.
  Une archive par mémoire ; référence à une version et éventuellement à une soutenance ; visibilité publique/privée, mots-clés JSON, option de publication de la note.

- Audit et infrastructure : audit_logs ; migrations de cache et de jobs. Aucune migration dédiée à la table Laravel notifications n’a été trouvée.

Points d’intégrité :

- La validation de program_id et department_id vérifie leur existence, pas leur cohérence entre eux.
- Les contrôles applicatifs de suppression de programmes, années ou départements ne couvrent pas toujours toutes les références imposées par les clés étrangères. Une suppression peut donc échouer au niveau DB.
- La relation entre thesis_archives.thesis_version_id et le mémoire de l’archive n’est pas une contrainte du schéma et n’est pas vérifiée par le service.
- Les suppressions logiques ne déclenchent pas les cascades SQL prévues pour les suppressions physiques.
- La migration 2024_01_06_144440_create_defense_jury_evaluations_table.php précède, par son nom, les migrations 2026 des tables defense_schedules et jury_members qu’elle référence. Sur un moteur qui exige les tables référencées à la création de la contrainte, l’ordre peut faire échouer la migration.
- Le schéma réel, les migrations appliquées, les données présentes et les éventuelles tables ajoutées hors migrations n’ont pas été vérifiés.

======================================================================
F. AUTHENTIFICATION ET AUTORISATIONS
======================================================================

Mécanismes présents :

- Les routes métier utilisent principalement auth:sanctum et le middleware active.
- Les jetons sont créés à la connexion, révoqués à la déconnexion et régénérés après réinitialisation ; une nouvelle connexion supprime les jetons précédents du compte.
- config/sanctum.php définit une expiration à 43 200 minutes ; la configuration effective au runtime n’a pas été vérifiée.
- Les mots de passe sont hachés par Laravel et soumis à des règles minimales de complexité.
- Les alias role, permission et active sont définis dans bootstrap/app.php. Les policies sont enregistrées dans AuthServiceProvider.php.

Lacunes et risques :

1. CRITIQUE — élévation de privilèges à l’inscription. Le rôle est contrôlé uniquement par l’existence de son ID, pas par une règle limitant le rôle sélectionnable.
2. Accès transversal aux mémoires. ThesisPolicy::viewAny retourne true et ThesisController::index ne filtre pas selon le rôle ou la participation. Les filtres student_id et supervisor_id ne remplacent pas un contrôle d’accès. La ressource retourne notamment nom complet, numéro étudiant, résumé et statut.
3. Accès transversal aux informations de soutenance. DefenseSchedulePolicy::view et generateReport retournent true ; le calendrier est également autorisé sans contrôle de rôle. Le PDF expose identité de l’étudiant, jury et, si disponible, résultat et remarques.
4. Profils encadreur consultables largement. viewAny et view de SupervisorPolicy autorisent toute consultation ; les ressources incluent email et téléphone.
5. Autorisations administratives incomplètes. DELETE /api/admin/academic-years/{academic_year} n’est pas accompagnée d’un Form Request ni d’un appel à une policy administrateur. Accessible à tout compte actif authentifié, sous réserve du contrôle de dépendance.
6. Archives privées révélées par recherche. Le orWhereJsonContains de ThesisArchiveService::query peut contourner le filtre visibility=public dans la liste publique.
7. Données personnelles publiques. Une archive publique expose par conception les noms de l’étudiant, de l’encadreur et des jurés, ainsi que résumé et informations de soutenance ; la note dépend de show_final_grade.
8. La vérification d’email existe, mais aucune protection verified n’est appliquée aux groupes de routes.
9. Fuite d’existence de comptes. La validation d’email et les réponses de réinitialisation distinguent adresse existante et absente ; la route forgot-password est limitée à trois requêtes par minute.
10. Plusieurs liens entre identifiants existants ne sont pas vérifiés métier : version du commentaire/mémoire, programme/département, version archivée/mémoire.
11. bootstrap/app.php renvoie des formats JSON dédiés pour validation, authentification, autorisation et modèle introuvable. En production non-debug, les autres exceptions deviennent un 500 générique. Les exceptions métier qui posent simplement leur code PHP à 422 ne sont pas converties explicitement en réponse HTTP 422.

======================================================================
G. WORKFLOW DES MÉMOIRES ET SOUTENANCES
======================================================================

Transitions définies dans le code actuel par ThesisService :

- draft -> submitted
- submitted -> under_review
- under_review -> revision_required, approved ou rejected
- revision_required -> submitted
- approved -> aucune transition dans l’état actuel du fichier modifié
- rejected -> aucune transition
- archived -> aucune transition

Le dépôt d’une première version ne soumet pas automatiquement le mémoire. La soumission exige au moins une version et crée un historique. L’affectation d’encadreur est une action distincte. Le changement de statut crée un historique et déclenche une notification.

Soutenances et archivage :

1. Une soutenance peut être créée pour un mémoire et une salle ; le schéma ne permet qu’une soutenance par mémoire.
2. Le jury est affecté avec un président, un examinateur et un rapporteur ; les collisions de disponibilité et l’affectation du directeur comme juré sont contrôlées partiellement.
3. Chaque juré affecté peut soumettre ou remplacer son évaluation.
4. Un résultat final est enregistré séparément et fait passer la soutenance à completed. Il n’est pas calculé à partir des évaluations individuelles.
5. L’archivage vérifie que le mémoire est approuvé, qu’une version PDF existe, que la soutenance est terminée et que le verdict n’est pas fail.
6. L’archivage crée l’enregistrement d’archive puis modifie directement le statut du mémoire en archived. Ce changement direct n’ajoute pas d’entrée à thesis_status_histories.

Aucun contrôle explicite n’impose le statut du mémoire avant la planification d’une soutenance. Le statut postponed est prévu par le schéma et les filtres, mais aucun chemin de transition correspondant n’a été identifié. Ces transitions décrivent le code ; elles ne prouvent pas les transitions actuellement enregistrées en base.

H. FICHIERS ET TRAITEMENTS DES DOCUMENTS
======================================================================

- Les versions de mémoire sont placées sur le disque local, dont la racine configurée est storage/app/private dans config/filesystems.php. Elles ne sont pas destinées à une exposition statique publique.
- Les dépôts acceptent PDF, DOCX et ZIP, avec une limite de 20 Mo dans le Form Request et dans le service. Aucun contrôle antivirus ou analyse du contenu n’a été trouvé.
- Le chemin de stockage est généré côté serveur. Le nom original et le type MIME sont conservés comme métadonnées et le téléchargement passe par un endpoint autorisé.
- Le téléchargement d’une version vérifie que cette version appartient bien au mémoire passé dans l’URI.
- Le téléchargement d’une archive publique vérifie la visibilité, mais dépend de la version référencée dans l’archive ; l’appartenance et le type de cette version ne sont pas revalidés.
- Le service d’archivage peut accepter un thesis_version_id d’un autre mémoire ou non-PDF. Cela peut conduire à exposer le mauvais document par le téléchargement d’archive.
- Les écritures de fichiers effectuées pendant une transaction DB ne sont pas annulées automatiquement par un rollback. Inversement, la suppression d’un fichier dans une transaction ne restaure pas le document si la suppression DB échoue.
- Les avatars sont enregistrés sur le disque public après validation d’image, avec une limite de 2 Mo ; l’ancien fichier est supprimé avant le nouvel enregistrement du profil, sans transaction commune fichier/base.
